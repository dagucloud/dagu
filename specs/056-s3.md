# Spec: S3 Actions

## Status

Implemented.

This spec defines conformance behavior for the built-in `s3.upload`,
`s3.download`, `s3.list`, and `s3.delete` actions.

## Scope

This spec covers:

- the required `with.bucket` (all operations), and how it, along with
  connection fields (`with.endpoint`, `with.region`,
  `with.access_key_id`, `with.secret_access_key`, `with.session_token`,
  `with.profile`, `with.force_path_style`), can be set once in a
  DAG-level `s3:` block and inherited by every step, with a step's own
  `with:` fields overriding the DAG-level value
- `with.endpoint` and `with.force_path_style`, which target an
  S3-compatible service (this spec's own tests run against one) rather
  than AWS itself
- `s3.upload`'s required `with.source` and `with.key`, and
  `with.content_type`, `with.storage_class`, `with.metadata`,
  `with.tags`, `with.acl`, `with.sse`/`with.sse_kms_key_id`
- `s3.download`'s required `with.key` and `with.destination`
- `s3.list`'s `with.prefix`, `with.recursive` (default `false`: groups
  keys sharing the next path segment after `with.prefix` into a single
  common-prefix entry instead of listing them), and `with.output_format`
  (`json`, the default, or `jsonl`)
- `s3.delete`'s single-key form (`with.key`) versus its by-prefix form
  (`with.prefix`, always recursive regardless of `with.recursive`)
- that every operation's error is wrapped under one generic sentinel per
  operation, so a missing key, a missing bucket, and bad credentials are
  not distinguishable by exit code, only by the wrapped message text
- that every configuration error this spec documents is rejected at
  DAG-build-time validation, not only at runtime -- except where noted,
  since this executor's registered step validator does not rerun full
  configuration validation
- a build-time/runtime validation split for numeric fields that admit an
  explicit `0`: the JSON Schema's minimum rejects an explicit `0` for
  `with.part_size` and `with.concurrency` at build time, even though the
  Go configuration code treats `0` as "use the default" and would accept
  it if it ever reached that code
- validation and runtime errors

This spec does not define:

- behavior against real AWS S3 specifically (this spec's own tests run
  against a local S3-compatible server); AWS-only behavior such as
  storage-class tiering enforcement is out of scope
- multipart upload internals beyond `with.part_size`/`with.concurrency`
  existing as tuning knobs
- `with.tags`, `with.metadata`, or `with.acl`'s effect beyond being
  accepted and passed through -- this spec does not verify their
  server-side effect
- direct `type: s3` authoring

## Goal

Workflow authors move objects to, from, and within an S3-compatible
object store as DAG steps -- uploading a build artifact, downloading a
dependency, listing or deleting objects under a prefix -- without
shelling out to a separate S3 client.

## Behavior

### Connection configuration

`with.bucket` and the connection fields (`with.endpoint`,
`with.region`, `with.access_key_id`, `with.secret_access_key`,
`with.session_token`, `with.profile`, `with.force_path_style`,
`with.disable_ssl`) may be set once in a DAG-level `s3:` block, in the
same field names as `with:`. Every step of every `s3.*` operation
inherits those values as defaults; a field set in the step's own
`with:` overrides the DAG-level value for that step only.

### Upload

`s3.upload` requires `with.source` (a local file path) and `with.key`.
`with.content_type`, when unset, is inferred from `with.source`'s file
extension, falling back to `application/octet-stream`. `with.storage_class`
and `with.acl`, when set, must be one of a fixed set of recognized
values. `with.sse: aws:kms` requires `with.sse_kms_key_id`.

### Download

`s3.download` requires `with.key` and `with.destination` (a local file
path); missing parent directories are created first.

### List

`s3.list` requires only `with.bucket` (inherited or explicit).
`with.prefix` filters by key prefix. Without `with.recursive`, keys
sharing a path segment after `with.prefix` are collapsed into a single
entry named for that shared segment (a "common prefix"), the way a
directory listing would show a subdirectory without descending into
it; with `with.recursive: true`, every matching key is listed
individually regardless of nesting. `with.output_format: jsonl` writes
each object as its own JSON value directly, instead of collecting them
into the default single JSON result's `objects` array.

### Delete

`s3.delete` requires `with.key` or `with.prefix`. `with.key` deletes
that single object. `with.prefix` deletes every object whose key has
that prefix, at any depth, regardless of `with.recursive` (which has no
effect on delete).

### Error wrapping

Every operation wraps whatever error it encounters under one sentinel
for that operation (upload, download, list, or delete): a missing key,
a missing bucket, and invalid credentials all surface as the same kind
of error and the same non-zero exit code for a given operation, distinguishable
only by the human-readable message text the underlying S3 client
produced, not by the error's category.

## Errors

### Validation

The registered step validator for `s3.*` checks only that an operation
is named; it does not rerun the full configuration validation. As a
result, only the following are rejected at DAG-build-time validation
(`dagu validate`), enforced by JSON Schema:

- `with.part_size` set to `0` or a value below `5`: a schema `minimum`
  error -- even though the Go configuration code treats an explicit `0`
  as "use the default part size," that value never reaches that code.
- `with.concurrency` set to `0` or a negative value: a schema `minimum`
  error, for the same reason.
- `with.sse` set to a value other than `AES256` or `aws:kms`: a schema
  `enum` error.
- `with.output_format` set to a value other than `json` or `jsonl`: a
  schema `enum` error.

All other configuration errors below pass `dagu validate` and surface
only when the step actually runs:

- `with.bucket` missing (DAG-level and step-level): an error containing
  `"bucket is required"`.
- `s3.upload` without `with.source` or `with.key`: an error containing
  `"source is required for upload"` or `"key is required for upload"`.
- `s3.download` without `with.key` or `with.destination`: an error
  containing `"key is required for download"` or `"destination is
  required for download"`.
- `s3.delete` without `with.key` or `with.prefix`: an error containing
  `"key or prefix is required for delete"`.
- `with.storage_class` or `with.acl` set to an unrecognized value: an
  error containing `"invalid storage class"` or `"invalid acl"`.
- `with.sse: aws:kms` without `with.sse_kms_key_id`: an error containing
  `"sse_kms_key_id is required when sse is 'aws:kms'"`.

### Runtime

- `s3.upload` with a local `with.source` that does not exist: an error
  containing `"s3: source not found"`.
- Any operation against a bucket or key that does not exist, or with
  invalid credentials: an error containing `"s3: <operation> failed"`
  (for example, `"s3: download failed"`), wrapping the underlying S3
  client error.

## Examples

Upload a build artifact using DAG-level connection defaults:

```yaml
s3:
  bucket: my-artifacts
  region: us-east-1
steps:
  - action: s3.upload
    with:
      source: ./dist/app.tar.gz
      key: releases/app.tar.gz
      storage_class: STANDARD_IA
```

List and then delete everything under a prefix:

```yaml
s3:
  bucket: my-artifacts
steps:
  - id: list
    action: s3.list
    with:
      prefix: tmp/
      recursive: true
  - id: clean
    depends: list
    action: s3.delete
    with:
      prefix: tmp/
```
