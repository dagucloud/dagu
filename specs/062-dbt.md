# Spec: DBT Action

## Status

Implemented.

This spec defines conformance behavior for the official remote action
`dbt@v1` (`dagucloud/dbt`).

## Scope

Like `node-script@v1` ([Spec 060: Node Script Action](060-node-script.md))
and `python-script@v1` ([Spec 061: Python Script
Action](061-python-script.md)), `dbt@v1` is not a built-in Go executor. It is
an official remote action: a git repository (`dagucloud/dbt`) containing a
`dagu-action.yaml` manifest and a DAG that runs a real `dbt` Core CLI the
action provisions via `uv` (independent of any system-installed Python or
dbt). Referencing `dbt@v1` resolves through Dagu's generic remote-action
mechanism, which clones the action's repository and provisions its pinned
`uv`/Python/dbt toolchain on first use.

This spec covers:

- the required `with.projectDir` and the structured inputs the action turns
  into a real `dbt` command line: `command`, `requirements`, `profilesDir`,
  `profile`, `target`, `select`, `exclude`, `selector`, `vars`, `threads`,
  `state`, `targetPath`, `logPath`, `fullRefresh`, `failFast`, `warnError`,
  `defer`, `quiet`, `args`, `env`, `pythonVersion`, `timeoutSeconds`
- the result object: `ok`, `exitCode`, `command`, `stdout`, `stderr`,
  `durationMs`, `targetPath`, `logPath`, and the conditional
  `manifestPath`/`runResultsPath`/`catalogPath`/`sourcesPath` fields
- that a non-zero `dbt` exit -- an invalid `--project-dir`, a dbt profile
  whose adapter package was never installed, exceeding `with.timeoutSeconds`
  -- and an unresolvable `with.requirements` entry (a `uv run --with`
  resolution failure) are both reported through the ordinary
  `exitCode`/`stdout`/`stderr` fields with `ok: false`, not through the
  outputs schema's separate `error` object
- that a later step reads a result field as `${<step id>.outputs.<path>}` (a
  bare-step-id reference), the same form confirmed for `node-script@v1` and
  `python-script@v1`, and not via the strict
  `${steps.<step id>.outputs.<name>}` form
- that `dagu validate` never resolves a remote action reference: a `dbt@v1`
  step passes validate regardless of its `with:` content, and
  `with.projectDir` being required is enforced only once the step actually
  runs

This spec does not define:

- the dbt action's own implementation, versioning, or release process --
  this spec treats `dbt@v1` as an external dependency and documents its
  observed contract
- `dbt` Core's own command semantics, adapter behavior, or artifact file
  formats (`manifest.json`, `run_results.json`, `catalog.json`,
  `sources.json`) beyond that Dagu surfaces their paths when present
- the generic remote-action resolution mechanism itself, or the
  `${<step id>.outputs.<path>}` reference form's own resolution mechanism --
  both are covered in more depth by [Spec 060: Node Script
  Action](060-node-script.md) and [Spec 007: Value Resolution
  Steps](007-value-resolution-steps.md)
- `uv`'s own dependency resolution behavior beyond that an unresolvable
  requirement fails the step
- performance or caching behavior of the action's own tool provisioning

## Goal

Workflow authors run real `dbt build`/`run`/`test` (and related) commands
against a real dbt project as a Dagu step, without installing or managing
Python, dbt, or a dbt adapter package themselves.

## Behavior

### Input

`with.projectDir` is required: an absolute path (or a path otherwise
meaningful on the worker that runs the action) to the directory containing
`dbt_project.yml`. `with.command` selects which `dbt` subcommand runs
(`build`, `run`, `test`, `seed`, `snapshot`, `compile`, `debug`, `parse`,
`list`, `ls`, `show`, `run-operation`, `deps`, `clean`, `docs generate`, or
`source freshness`) and defaults to `build`. `with.requirements` is a list of
pip-compatible package specifiers installed via `uv run --with` before `dbt`
runs, and defaults to `["dbt-core"]` -- a project that needs a specific
adapter (for example DuckDB, Postgres) must list it explicitly (for example
`dbt-duckdb==1.10.1`), since the default has no adapter package at all.

`with.profilesDir`, `with.profile`, `with.target`, `with.select`,
`with.exclude`, `with.selector`, `with.vars`, `with.threads`, `with.state`,
`with.fullRefresh`, `with.failFast`, `with.warnError`, `with.defer`,
`with.quiet`, and `with.args` each map to a corresponding `dbt` CLI flag
(`--profiles-dir`, `--profile`, `--target`, `--select`, `--exclude`,
`--selector`, `--vars`, `--threads`, `--state`, `--full-refresh`,
`--fail-fast`, `--warn-error`, `--defer`, `--quiet`, and raw trailing
arguments, respectively) when set; an object value for `with.vars` is
encoded as compact JSON. `with.targetPath`/`with.logPath` map to
`--target-path`/`--log-path` and, when unset, each defaults to a directory
inside the action's own per-run work directory rather than a path inside
`with.projectDir`. `with.env` is an object of extra environment variables
exposed to the real `dbt` process (in addition to the process environment
the action itself inherits). `with.pythonVersion` selects the `uv`-managed
Python version (default `3.13.9`). `with.timeoutSeconds` bounds how long the
`dbt` process may run (default `3600`).

### Execution

The action builds one real command line -- `uv run --isolated --python
<pythonVersion> --with <requirement> ... dbt <command tokens>
--project-dir <projectDir> [--profiles-dir ...] ... --target-path <path>
--log-path <path> [--select ...] ... [--vars <json>] [--threads N]
[--full-refresh] ... [args...]` -- and runs it as a real subprocess, with
`with.env`'s entries merged into that subprocess's environment. The
resulting argv is reported back verbatim as the result's `command` field (a
JSON array of strings), in the order above.

### Result

The step's stdout is one JSON object:

- `ok`: `true` when the `dbt` process exited with code `0`.
- `exitCode`: the `dbt` process's real exit code (for example `2` for a
  `dbt` CLI usage error, `124` when `with.timeoutSeconds` was exceeded).
- `command`: the full argv used to invoke `dbt` through `uv`.
- `stdout`/`stderr`: the `dbt` process's own captured stdout and stderr.
- `durationMs`: wrapper-measured `dbt` process duration.
- `targetPath`/`logPath`: the effective (resolved) target and log
  directories.
- `manifestPath`/`runResultsPath`/`catalogPath`/`sourcesPath`: present only
  when, respectively, `manifest.json`, `run_results.json`, `catalog.json`,
  or `sources.json` exists under `targetPath` after the process exits (for
  example, `manifest.json`/`run_results.json` after `build`/`run`/`test`,
  `catalog.json` after `docs generate`, `sources.json` after `source
  freshness`). A command that never produces one of these files (for
  example `debug`, or a `build` invocation that failed before parsing the
  project) omits the corresponding field entirely rather than reporting it
  as empty.
- `error`: an object (with at least a `message` field) the outputs schema
  reserves for a wrapper-level failure -- one where the action's own script
  raises before it can run `dbt` at all. In practice this is not reached for
  a step that already passed the action's input schema: every condition the
  wrapper itself would reject (an unsupported `command` value, a
  non-string/non-boolean/non-integer field of the wrong type) is already
  rejected by that same input schema before the wrapper ever runs. A bad
  `with.projectDir`, a dbt profile whose adapter was never installed, an
  unresolvable `with.requirements` entry, and exceeding
  `with.timeoutSeconds` are, instead, all real process outcomes reported
  through the ordinary `ok`/`exitCode`/`stdout`/`stderr` fields described
  above, not through `error`.

### Downstream references

A later step reads a field of the result as `${<step id>.outputs.<path>}` --
the step ID used directly as the reference's namespace, with `<path>` able
to drill into a nested field of the returned object. This matches the
behavior [Spec 060: Node Script Action](060-node-script.md) and [Spec 061:
Python Script Action](061-python-script.md) document, confirming it is a
property of remote action:-type steps generally, not specific to one
action. The strict `${steps.<step id>.outputs.<name>}` form documented for
declared step outputs (see [Spec 012: Step Outputs](012-step-outputs.md))
does not resolve for a `dbt@v1` step, for the same reason it does not for
`node-script@v1` or `python-script@v1`.

## Errors

### Validation

- An action reference missing its required `@version` suffix (for example,
  `dbt` instead of `dbt@v1`): an error containing `unknown action`. This is
  enforced generically for any action reference, not specifically for
  `dbt`.

`dagu validate` does not resolve the remote action reference at all, so it
cannot check `dbt@v1`'s own requirements (such as `with.projectDir` being
required, or `with.command` being restricted to a fixed set of dbt
subcommands) -- a step missing `with.projectDir`, or one with an
unsupported `with.command` value, passes validate.

### Runtime

- `with.projectDir` missing: an error containing `missing properties:
  ["projectDir"]`, raised when the action resolves its own input schema
  against the step's `with:` content -- before `uv` or `dbt` is ever
  invoked.
- `with.command` set to an unsupported value: an error containing `enum:`
  and the value, raised by the same input-schema check, before `uv` or
  `dbt` is ever invoked.
- A nonexistent `with.projectDir`, a `dbt` profile whose adapter package is
  not in `with.requirements`, or any other `dbt` CLI usage or runtime
  failure: the step fails (a non-zero exit) with `ok: false`, a non-zero
  `exitCode`, and the diagnostic text in `stdout`/`stderr`, exactly as `dbt`
  itself reported it.
- An unresolvable `with.requirements` entry: `uv run --with` itself fails
  before `dbt` starts, reported as `ok: false`, `exitCode: 1`, and `uv`'s
  own dependency-resolution output in `stderr` -- not as a step- or
  action-level wrapper error.
- Exceeding `with.timeoutSeconds`: the step fails with `ok: false`,
  `exitCode: 124`, and a `dbt command timed out after <n>s` message
  appended to `stderr`.

## Examples

Build a DuckDB-backed dbt project and read the run's exit code from a later
step:

```yaml
steps:
  - id: dbt_build
    action: dbt@v1
    with:
      projectDir: /data/jaffle-shop
      profilesDir: /data/dbt-profiles
      requirements:
        - dbt-duckdb==1.10.1
      command: build
      targetPath: /data/artifacts/dbt-target
      logPath: /data/artifacts/dbt-logs

  - id: print_summary
    depends: dbt_build
    run: |
      echo "dbt exit code: ${dbt_build.outputs.exitCode}"
      echo "dbt run results: ${dbt_build.outputs.runResultsPath}"
```

Bound a run with a timeout:

```yaml
steps:
  - action: dbt@v1
    with:
      projectDir: /data/jaffle-shop
      command: run
      timeoutSeconds: 300
```
